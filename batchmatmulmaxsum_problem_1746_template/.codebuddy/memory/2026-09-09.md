## 三、新根因候选（高度契合观察）— dtype 枚举语义

- 模板注释/本地 main.asc 使用自造枚举：1=fp16、2=bf16（`TensorInfo.dtype`）。
- CANN 真实 aclDataType（头库 asc/impl/utils/debug/asc_debug_types.h 与 kernel_utils_dump_constants.h）：
  `ACL_FLOAT=0, ACL_FLOAT16=1, ..., ACL_BF16=27`。
- 原 kernel.asc 判 `isBf16 = (dtypeCode == 2)`。若 judge host 用 acl 码填充 dtype，则：
  - fp16 点 dtype=1 → 走 fp16 kernel → PASS（恰好 2 个，对应点 1/5）；
  - bf16 点 dtype=27 → 被误判为 fp16 → 用 fp16 kernel 读 bf16 位型 → 大值垃圾 → WA（点 2-9）；
  - 大 bf16 点仍 TLE（点 10）、更大被 Skip（点 11-15）。
- 该假设同时解释「转置修复后结果不变」：dtype 判定代码两版相同。

## 四、修复（no-regret，零风险）

- kernel.asc run_kernel：`isBf16 = (dtypeCode != 1)`。两种编码 fp16 都 ==1；输入仅 fp16/bf16，
  「非 1 即 bf16」在模板枚举（2）与 acl 枚举（27）下都正确。
- 本地 main.asc 增 `BMM_ACL_DTYPE=1` 模拟 judge acl 码喂入（manifest dtype 2 → TensorInfo.dtype 27），
  可云验两种喂法同结果，直接证明修复覆盖面。
- gen_data_casematrix.py 增官方域用例 cid 220-233（奇小 shape + tx 组合 + 全负 + 长 K 等）。

## 八、探针 2 判题结果（2026-09-09 傍晚）+ 探针 3 启动

- 探针 2（commit 6f41095，aclrtMallocHost→malloc/free）云验三组全绿后重提判题：
  **仍 2P+7WA+1TLE+5SKIP，逐点不变** → host 内存申请 API 不是根因，aclrtMallocHost 失败假设排除。
- 推论收窄：7 WA 转置点挂了三种 host 内存申请方式（aclrtMallocHost / malloc）后依然一致 → 问题不在
  「host 内存能否申请」，而在 normalize 的**语义**或 **aclrtMemcpy/同步 D2H/H2D 在 judge 的可用性**。
- 探针 3（本 commit）：把 `kernel.asc` run_kernel 中 `if (transposeX1 || transposeX2)` 改为 `if (false)`，
  **彻底跳过 host normalize**，x1/x2 原始指针直接当逻辑行优先送入 v1 kernel。
  - 判别矩阵：
    - judge tx 点数据本就逻辑布局 + tx 标志失真（多余/误设）→ 点 2-9 应 WA→PASS，收工（保留忽略标志版）。
    - judge tx 点数据确为物理转置 → 点 2-9 仍 WA，与现状同 → 证数据真转置、且 host normalize 语义正确，
      差异只剩 judge 环境不支持 host 侧 aclrtMemcpy/同步 → 转兜底「核内转置」。
  - 本地预期：run.sh 0-9（无 tx）与 casematrix 非 tx 例全绿；所有 tx 例（含 201/204-210/221-223/225-227/
    229-233 等）会 WA —— **这是探针的预期副作用，不是回归**。
- 探针 3 判题结果：**仍 2P+7WA+1TLE+5SKIP，逐点不变**；本地 casematrix 非 tx 例全绿、tx 例全 WA，与预期一致。
  → judge 的 tx 数据**确实是物理转置**，host normalize 语义正确；根因进一步锁死为 judge harness 中
  run_kernel 内部无法做 `aclrtMemcpy` D2H/H2D（与 host 内存申请无关）。
- 兜底 v1（commit a6c3a57）：**device-side 转置** staging（aclrtMalloc + `p1746_dev_transpose_x1/x2` 向量核，
  同 stream，无 D2H/H2D）。云验本地 34 例 casematrix **全绿**（含全部 tx），run.sh 10/10。
  判题结果：**仍 2P+7WA+1TLE+5SKIP 逐点不变** → device staging + `aclrtMalloc` 在 judge 同样不可用/被拒，
  每次 tx 点在 `aclrtMalloc` 失败后提前 return → y 未写 → WA。根因锁定：**judge 环境中 run_kernel 内任何
  host 侧内存/设备内存运行期 API（aclrtMalloc/Memcpy/Host）都不可用**，能用的只有 `<<<>>>` kernel launch + stream。
- 兜底 v2（当前 commit，已实施待云验）：**纯核内按物理布局读取，彻底去除所有运行期 API**。
  - p1746_run/fp16/bf16 增 tx1/tx2 形参；v2 cube 门控增加 `!tx1 && !tx2`（cube 只吃逻辑行优先，转置走 v1）。
  - 非转置：完全保持原路径（contiguous DataCopyPad 向量块）。
  - 转置：逻辑行变物理列 → 用**单元素掩码块 DataCopyPad**（`{1, sizeof(RawT), 0,0,0}`，dst=raw[j]）逐元素
    gather 到 local 16 位块再 Cast。选择单块而非多块 2 字节 stride 拷贝：后者块间 32B 相位不可控、
    语义不保证；单块掩码拷贝是本工程已验证可靠的最小原语。
  - 代价：转置输入的元素读变成逐元素 MTE，量级与向量读相同但指令数多；本地 tx 例都小/中，可接受。
  - 语义仍是 k 升序逐项累加 → 与 ff 路径/ golden 同序，本地应保持逐位一致。
  - 云验预期：run.sh 10/10、casematrix 34/34 全绿。
  - 若仍 2/15：说明连 kernel 内 GM 逐元素掩码读取/该 gather 思路也被拒 → 则只剩把转置折叠进数学结构的
    n-outer dot 变体（ft/tf/tt 各自重排，只对转置输入读一次）+ 复检 judge 数据是否真转置。
