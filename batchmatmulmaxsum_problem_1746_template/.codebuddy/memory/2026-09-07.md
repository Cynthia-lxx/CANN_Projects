## v1 kernel.asc 定稿与事件同步结论（2026-09-07 收尾）

v1 真 kernel 已整文件落盘（Projects/batchmatmulmaxsum_problem_1746_template/kernel.asc），结构 = `p1746_run<RawT>` 行式算法（batch×row；zero row → x1 row masked 读+Cast→x1f → V_S 屏障 → k 标量×n-chunk AXPY → 每 chunk ReduceMax+Max 链 fold → acc[0] count-1 Add）+ fp16/bf16 两个非模板 `__global__`。改动原则：全程仿 bmm_p2_slice（云验证），标量只存在于 vector lane0，acc 放 VECOUT 队列，输出 4B DataCopyPad。

**本次头库定点的公开事件 API（已核对 asc/include/interface，可直接用，勿再扩散检索）**：
- `TPipe::FetchEventID(HardEvent evt)` → 返回 `TEventID`（kernel_tpipe.h 公开成员）。
- `template<HardEvent event> AscendC::SetFlag(int32_t eventID)` / `WaitFlag(int32_t eventID)`（kernel_operator_block_sync_intf.h 公开声明；实现切到 `HardEvent::V_S` → `PIPE_V→PIPE_S`）。
- `HardEvent` 是 `AscendC` 命名空间内 `enum class`（MTE2_V/V_MTE2/MTE3_V/V_MTE3/V_S/S_V 等）。
- **不要用** `AscendC::event_t` / `AscendC::GetTPipePtr()`（内部/全局归属未确认），用自己局部 `TPipe pipe` 对象 + int32_t 即可。规范片段：
  `int32_t e = static_cast<int32_t>(pipe.FetchEventID(AscendC::HardEvent::V_S));`
  `AscendC::SetFlag<AscendC::HardEvent::V_S>(e); AscendC::WaitFlag<AscendC::HardEvent::V_S>(e);`
- V_S 事件每行 fetch 一次、Set 后立即 Wait，同一 id（=0）可跨行复用，勿需 Release（该过载不占位；ReduceSum impl 同款，QUE_MAX_EVENT 内）。
- 语义：GetValue 是裸 UB 标量读（无内建同步）；vector AXPY 乘子若走 `x1f[k]` 标量读，必须配 V→S 事件。acc/rm/part 等一律保持 vector lane0（ReduceMax→Max(rm,rm,part,1)→Add(acc,acc,rm,1)），绝不用 GetValue/SetValue 折叠。

**仍成立的事实（与判题崩溃解耦）**：v1 单核串行行式 vector 算法在判题档大 shape 上确实极慢（下 L121 代码实证 + case101 冒烟 2.05s/256³），因此 v2 提速动机不变、仍必须 cube；但这与 15 点统一 Fail 无因果关系。

**v1 为什么慢（代码实证 kernel.asc L126-213；性能事实与判题崩溃解耦，仍成立）**：单 block（grid=1）串行遍历全部 (b,m)；每行 k 用 `GetValue(x1f[k])` 标量读 + 内层 `for k` 里对**全 n 行做 DataCopyPad（GM→UB）**逐 k 重读 x2 → 复杂度 ≈ B·M·K·(N/64) 次带 GM 延迟的串行指令。本地 128³/512³ 估计 0.2s/~30s+ 量级，M=N=K≈1024 会到分钟级。

**规模挡板（已从 stage_goal 原文核实，供 v2 计算）**：
- B∈[1,64]；M/N∈[1,8192]；K∈[32,8192] 且 K%8==0。
- **B×M×K ≤ 2^28 且 B×N×K ≤ 2^28**（每输入张量元素上限）。
- 最坏组合下总 MACs ≈ 2^41（例 B=4,M=N=K=8192 合法；或 B=64,M=N=8192,K=512）。纯 vector 需 ~3×10^10 向量指令/核 → 必超时；**单核 cube 理论 <0.2s 可完成 2^41 MACs** → v2 必须 cube。

**关键头库事实（v2 架构分水岭）**：
- 910B = __NPU_ARCH__ 2201 (dav_c220)。`kernel_operator_atomic_intf.h` 的 `AtomicAdd/AtomicMax/AtomicCas/AtomicExch`（标量 GM 原子）**仅在 __NPU_ARCH__==5102||3510 编译期可用** → 2201 **无标量 GM 原子**。
- 因此「单 launch 内跨核归约（写 partial→核间同步→核 0 汇总）」在 910B **不可行**。
- **单 launch + 多核只能「按 batch 切分」**：每核负责不相交的 batch 全集并写自己 y[b]（输出天然互不相交、无同步）。B<核数时多余核空闲（核间不平行 B=1 的大 shape）。这是平台"恰 1 launch"约束下的硬架构事实。

## 探针 E：GetTensorC 产物"错内容 vs 错消费路径"双模式取证（2026-09-07 深夜追加）

**背景（探针 D 判读，见 cube_probe 目录 commit 7123d5b 输出）**：cube 小形状 mirror 连续拷贝显示 UB tile 行 0、1 全对，行 r≥2 内容=系数 63·(r-1)，精确等于 `golden[r-2]·(K-1)/K`（缺 1 项 k 的部分和，非本形状 C 任一行）；copy_sem_probe 已洗清 DataCopy gap 语义（srcGap=4=跳行、dstGap=4=行距 blockLen+gap，纯正无混读）。嫌疑锁定 L0C→UB 产物或消费时序。

**本轮改动（已静态核对，0 lint；改动只在 cube_probe/off host+kernel 探针层）**：
1. `cube_probe/cube_probe.asc`（P1 v3）：类加 `uint32_t mode`；
   - mode0 `cube_probe`：GetTensorC→EnQue→DataCopy（原路径逐字不变）；
   - mode1 `cube_probe_abs`：GetTensorC→**就地 Abs(cTileLocal,cTileLocal,baseM*baseN)→EnQue**→DataCopy（官方 vector 消费顺序，数据全正=纯屏障），mirror 侧带分带 [M*N,+1024)/(+1024,+2048)。
   - host 双 launch、双侧带+双主区 dump，逐行判型 G（=golden[r]）/P（=(K-1)/K·golden[r-2]）/S（main 区 =(K-1)/K·golden[m-1]）/0/x。
2. `off_matmul_abs.asc` host 追加 8×5 tile 网格 rel-bad 计数（perfect tile 数）与 row0 baseN 边界列归属映射 `x=(got-0.5)/K` 打印。kernel 逐字未动。
3. 判读：mode1 若行 r≥2 变对 → 之前 junk 是读早/时序（Abs 迫使 vector 消费同步）；若仍 junk → L0C→UB 内容本身错，与消费路径无关，转 tile 几何/迭代语义取证。

**头库核实结论（已与 cann_ascendc_headers_9.0.0 核对，asc 树为权威）**：
- `matmul_impl_base.h`：`template<bool sync=true> bool Iterate(bool enPartialSum=false)`→ScheduleOnce；本地 C 版 `template<bool sync=true> void GetTensorC(const LocalTensor<DstT>&, uint8_t enAtomic=0, bool enSequentialWrite=false)`，C pos=VECIN 时走 Scheduler->GetResult。我们的 `GetTensorC<true>(t,false,true)` 语义成立。
